## Что уже обнаружено в проекте

Проверь эти наблюдения по актуальной рабочей копии, прежде чем редактировать:

- config/cache.php содержит serializable_classes=false. Не ослабляй это ограничение.
- StoreController заново читает товары и категории для home(), catalog() и product().

- catalog() поддерживает q, category, sort, page; категория включает все уровни потомков.
- Пагинация через paginate(12)->withQueryString(); поиск экранирует LIKE-символы через likePattern().
- Карточка товара содержит variants, images, specifications, brandRecord, manufacturer и breadcrumbs.
- Product/Category используют YAML-переводы перед name_translations/description_translations.
- В props есть localized_name, localized_description, available, display_price и pricing_error.
- MarketContext хранит страну/язык в сессии и кеширует GeoIP по SHA-256 IP на 30 дней.
- ExchangeRateService хранит курсы в БД и мемоизирует их в $resolved внутри singleton-сервиса.
- Курсы младше 6 часов считаются свежими; при сбое источников используется последний сохранённый курс.
- Если курс отсутствует, возвращается DomainException; EUR имеет курс 1.
- Внешние источники курсов имеют timeout 4 секунды; GeoIP — 2 секунды.
- commerce:refresh-exchange-rates вызывается scheduler каждый час, но сейчас использует rate(),
  поэтому не обязательно выполняет фактическое обновление свежего курса.
- TranslationCatalog — singleton: парсит lang/store.yaml и мемоизирует каталоги en/ru/pl в памяти.
- HandleInertiaRequests добавляет auth.user, market, countries, translations и flash.
- PlaceOrder резервирует stock через decrement() внутри DB::transaction() с lockForUpdate().
- EloquentAdminOrderRepository возвращает stock через increment() при отмене заказа внутри транзакции.
- phpunit.xml использует CACHE_STORE=array и SESSION_DRIVER=array; БД тестирования называется testing.

## Выбор хранилища

Используй существующий Redis через Laravel Cache. Не добавляй отдельную библиотеку Redis без необходимости.
Предпочти отдельный настраиваемый store для кеша витрины, чтобы не переносить автоматически сессии,
очереди, ограничения запросов и другие механизмы приложения на новое хранилище.
Сохрани удобные настройки для запуска через Sail и непосредственно на хосте.
Тесты должны явно выбирать array store; не хардкодь Redis внутри сервисов.

Кратко сравни Redis, Valkey, Memcached, Dragonfly, database и file применительно к этому проекту.
Объясни выбор существующего Redis. Не добавляй контейнеры конкурентов только ради сравнения.
Valkey можно рассматривать как совместимую альтернативу, но не меняй сервер автоматически.
Не обещай превосходство по скорости или памяти без одинаковых воспроизводимых измерений.

## Реализация кеша витрины

1. Вынеси чтение и кеширование каталога в небольшой сервис, сохранив архитектуру приложения.
   Не добавляй зависимости от Laravel/Redis в app/Domain.
2. Кешируй дерево категорий, потомков, счётчики, featured, страницы каталога, карточки и related.
   Избегай повторных SQL и повторных обходов одного дерева в рамках запроса.
3. Храни только массивы и скалярные значения. Даты сериализуй строками или timestamp.
   Не кешируй Eloquent models, Collections, paginator objects, Carbon и Inertia Response.
   Не включай разрешение на произвольную десериализацию PHP-классов.
4. Предпочти кешировать исходные публичные данные, а цены и локализацию применять при сборке props.
   Общий кеш не должен сохранять результат мутации модели методом priced() для другого рынка.
   Если кешируешь уже локализованные данные, обязательно включай locale и версию переводов в ключ.
   Если кешируешь региональные цены, включай country, market, currency, VAT и версию курса.
   Один eu_global недостаточен: страны EUR имеют разные ставки НДС.
5. Ключ каталога строй из валидированных параметров q, category, sort и page в стабильном порядке.
   Нормализация не должна менять текущую семантику поиска. Не включай произвольные query-параметры.
   Ограничь кеширование произвольного поиска и пустых страниц, чтобы не раздувать пространство ключей.
6. Ссылки пагинации строй для текущего запроса после чтения кеша.
   Не сохраняй URL/host/query string первого посетителя для следующих посетителей.
7. Сохрани 404 для неактивного, удалённого товара, старого slug и несуществующей категории.
   Route model binding может оставлять один SQL-запрос; не обещай ноль запросов любой ценой.
8. Все записи данных имеют конечный TTL. TTL и включение кеширования вынеси в конфигурацию.
   Стартовые ориентиры: категории 10 минут, списки 1–2 минуты, карточки 2–5 минут.
   Это настройки, а не измеренные оптимальные значения; корректность обеспечивается инвалидацией.
9. Для дорогих заполнений кеша используй atomic lock с ограниченным временем ожидания.
   Повторно проверь кеш после получения lock; при timeout не блокируй запрос бесконечно.
   Не используй устаревший кеш как источник истины для оплаты или резервирования остатков.

## Инвалидация

- Выбери простую схему: ограниченные группы/версии ключей или эквивалентное решение.
- Схема должна работать в array-тестах. Не используй Cache::tags() без проверки возможностей store.
- Для версий учитывай конкурентные изменения и вытеснение метаданных из Redis:
  отсутствие версии не должно возвращать старое поколение ключей.
- Инвалидируй после успешного commit при создании, обновлении и удалении Product, Category,
  ProductVariant, Brand, Manufacturer, ProductImage и ProductSpecification.
- Учитывай изменения цены, active, featured, slug, категории, stock, изображений и характеристик.
- Смена родителя категории влияет на breadcrumbs, потомков и агрегированные счётчики.
- Проверяй старые и новые связи при переносе товара или варианта между родителями.
- Проверь decrement()/increment() в заказе и отмене по установленному Laravel:
  observer не должен пропускать эти операции, а rollback не должен публиковать незавершённые данные.
- Массовые query-builder update/delete и каскадные удаления могут обходить model events.
  Найди существующие пути записи и обеспечь явную инвалидацию там, где она требуется.
- Добавь команду целевого сброса кеша магазина для импортов и ручных bulk-операций.
- Не используй глобальный Cache::flush(), FLUSHDB или FLUSHALL.
- Учти гонку: запрос, начавшийся до commit, не должен записать старые данные под новой версией.
- Объясни поведение при сбое Redis во время инвалидации и восстановлении соединения.
  Не обещай строгую свежесть только благодаря TTL; обозначь границу допустимого устаревания витрины.

## Курсы, переводы, GeoIP

- Добавь межзапросный кеш успешных курсов по валюте; сохрани source, quoted_at и правило свежести.
- Сохрани последнюю валидную запись в БД как источник восстановления; не придумывай курс при ошибке.
- EUR должен работать без внешних запросов. Не кешируй pricing_error надолго.
- Обновление курса должно инвалидировать его кеш и любую зависимую кешированную цену.
- Сделай реальное обновление в commerce:refresh-exchange-rates отдельным от чтения свежего кеша.
- Не выдавай долгий сетевой refresh за ускорение чтения. Предпочти обновление через scheduler.
  Если переносишь HTTP refresh из пользовательских запросов в scheduler, явно опиши изменение,
  обеспечь восстановление при пустом кеше и тесты для отсутствующего и устаревшего курса.
- Для TranslationCatalog добавь межзапросный кеш по locale и версии YAML/алгоритма flatten.
  Изменение lang/store.yaml должно обновлять переводы и зависимые локализованные данные.
  Сохрани fallback и legacy aliases. Не читай и не парси весь YAML на каждом cache hit.
- Существующую мемоизацию сохрани, но не допускай бесконечно устаревших данных при долгоживущем процессе.
- Проверь GeoIP: Cache::remember с null не обеспечивает устойчивое отрицательное кеширование.
  Используй явный sentinel для неуспешного определения с коротким TTL; успешное — как сейчас.
- Не меняй выбранную пользователем страну/язык и не кешируй целиком MarketContext с чужой сессией.

## Приватность, целостность и отказоустойчивость

- Не кешируй целые HTML/Inertia-ответы: они содержат auth.user, flash и market.
- Не кешируй в общем кеше корзины, checkout, заказы, адреса, аккаунты, Shop Pay и webhook-ответы.
- Расчёт заказа и проверка остатков продолжают читать актуальные данные БД и использовать транзакции.
- Не заменяй существующие блокировки БД кеш-блокировками.
- Ошибка чтения/записи необязательного кеша должна позволять читать исходные данные.
  Обрабатывай конкретные ошибки инфраструктуры; не скрывай ошибки SQL и приложения общим catch(Throwable).
- Предусмотри короткие сетевые timeout и наблюдаемость ошибок без логирования персональных данных.
- Не включай бесконтрольный кеш произвольных параметров и не создавай вечные payload-записи.
- Лимит Redis memory, eviction и запас памяти контейнера должны быть осознанными и документированными.
- Не распространяй политику вытеснения кеша на очереди/сессии: логические Redis DB не изолируют maxmemory.
- Сохрани текущие SESSION_DRIVER и QUEUE_CONNECTION. Не открывай Redis публично в production.

## Проверки

Добавь содержательные тесты поведения, а не только проверки вызовов Cache::remember:

- cache miss и hit дают одинаковые публичные данные; hit уменьшает запросы к таблицам каталога;
- после прогрева обновления товаров, цен, связей, stock и active видны следующему посетителю;
- создание/удаление и смена slug корректно обновляют списки, карточки, счётчики и 404;
- изменения stock через размещение и отмену заказа видны на витрине;
- commit/rollback и конкурентное заполнение не загрязняют новое поколение кеша;
- q/category/sort/page не смешиваются; поиск LIKE и ссылки пагинации сохраняют поведение;
- последовательные запросы BY, PL и двух EUR-стран не смешивают валюту, НДС и язык;
- запросы разных пользователей не смешивают auth, flash и market;
- обновление YAML и курса отражается без ожидания TTL зависимых данных;
- сбой кеша, вытеснение ключа и пустой кеш восстанавливаются предсказуемо;
- Redis round trip действительно возвращает массивы при serializable_classes=false;
- после операции заказа безопасность и денежные инварианты сохранены.

Основные тесты оставь независимыми от Redis. Интеграционные проверки Redis запускай отдельно,
с уникальным префиксом и удалением только тестовых ключей. Учти транзакции RefreshDatabase:
after-commit сценарии должны проверять реальный commit, а не оставаться неисполненными до rollback теста.
Не ослабляй старые assertions ради прохождения. Изменение ожидаемого поведения объясни отдельно.

Замерь до/после холодный и тёплый кеш для /, /shop и /shop/{slug} на одинаковых данных и рынке.
Отдельно проверь обычный HTML и Inertia-запросы. Зафиксируй SQL count и время ответа;
если доступен нагрузочный инструмент, дополнительно p50/p95, ошибки, CPU и память контейнеров.
Не запускай нагрузочный тест production и не считай одиночный локальный замер доказательством ускорения.
Если Docker или Redis недоступен, выполни доступные проверки и явно обозначь непроверенную часть.
